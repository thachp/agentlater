# Deploying AgentLater

Three Workers, each with `staging` and `production` environments in its `wrangler.jsonc`:

| Worker | Staging | Production | Public? |
| --- | --- | --- | --- |
| `apps/api` | `runlater-api-staging` | `runlater-api-production` | No — service binding only |
| `apps/gateway` | `runlater-gateway-staging` | `runlater-gateway-production` | Yes |
| `apps/web` | `runlater-web-staging` | `runlater-web-production` | Yes |

[`deploy.yml`](../.github/workflows/deploy.yml) runs after CI passes on `main`. It deploys staging, then
production once the `production` environment's reviewer approves. Each environment deploys
**api → gateway → web** ([`deploy-env.yml`](../.github/workflows/deploy-env.yml)); the gateway's service
binding fails if the API Worker doesn't exist yet.

Always pass `--env`. A bare `wrangler deploy` creates un-suffixed `runlater-api` / `runlater-gateway` /
`runlater-web` Workers from the top-level config.

## One-time setup

Nothing deploys until `DEPLOY_ENABLED` is set, so the workflow can merge before these steps are done.

1. **Cloudflare API token** — one per environment, scoped to the AgentLater account only (the account
   also holds unrelated Workers). Permissions:
   - Account · Workers Scripts · Edit
   - Account · D1 · Edit (from phase 4)
   - Account · Queues · Edit (from phase 3)
   - Account · Workers KV Storage · Edit (hosted MCP)
   - Zones `runlater.io` and `agentlater.io` · Workers Routes · Edit (only once custom domains are added to config)

   Give it an expiry and record the rotation date.
2. **GitHub environments** `staging` and `production` (Settings → Environments):
   - Both: restrict deployment branches to `main`.
   - `production`: add a required reviewer; disable admin bypass.
   - Secret in each: `CLOUDFLARE_API_TOKEN` (from step 1).
   - Everything else is generated by the setup script, which never prints a secret:

     ```bash
     node scripts/setup-deploy-secrets.mjs --account-id <cloudflare account id>
     ```

     It sets `CLOUDFLARE_ACCOUNT_ID`, `ASSERTION_PRIVATE_KEY`, `BETTER_AUTH_SECRET`, `SECRETS_KEY`, the
     `GATEWAY_PUBLIC_KEY` variable and (staging) `RECEIVER_TOKEN`, skipping any already set. `--rotate` replaces
     them all except `SECRETS_KEY`; the key pair always changes together. `SECRETS_KEY` seals every project
     secret, so replacing it alone makes every stored secret unreadable; rotate it with the steps in
     [Rotating `SECRETS_KEY`](#rotating-secrets_key). Without it the API still deploys, with a warning, and `set_secret` answers
     `503 secrets_unavailable`. The deploy workflow hands these to Cloudflare at deploy time
     (`--secrets-file` / `--var`), so nothing secret is committed or set with `wrangler secret put`.
   - Variable in each (once the gateway has a hostname): `GATEWAY_URL`, e.g. `https://gateway-staging.agentlater.io`. Setting it turns on the smoke check and, on staging, the required journey.
3. **Repository variable** `DEPLOY_ENABLED=true` (Settings → Secrets and variables → Actions → *Repository*
   variables). An environment variable of that name does nothing: the gate is evaluated before any
   environment is selected.
4. **First run** — trigger *Deploy* manually (`workflow_dispatch`) and watch it. Confirm in the dashboard
   that exactly the six expected Workers exist.

## Adding resources per phase

Wrangler doesn't inherit bindings into environments: every binding below goes in **both** `env.staging`
and `env.production`, with that environment's resource name.

### Phase 3 — API

- `compatibility_flags: ["global_fetch_strictly_public"]` on the API Worker.
- `durable_objects.bindings` for `TaskLedger`, plus `migrations: [{ "tag": "v1", "new_sqlite_classes": ["TaskLedger"] }]`.
- `analytics_engine_datasets` for `STATS`: `runlater_stats_staging` and `runlater_stats_production`. Each is
  created by its first write.
- Queues `runlater-ready-staging` and `runlater-ready-production` exist (created 2026-10-31). Each queue
  must exist before the first deploy that references it.
- Ed25519 assertion public key as a `vars` entry on the API (it's not secret).

### Phase 4 — Gateway

- D1 databases `runlater-gateway-staging` and `runlater-gateway-production` exist (created 2026-10-31); their
  ids are in `apps/gateway/wrangler.jsonc`. `deploy-env.yml` applies `apps/gateway/migrations` before the
  gateway deploys.
- Secrets and the API's `GATEWAY_PUBLIC_KEY`: generated by `scripts/setup-deploy-secrets.mjs` (one-time setup,
  step 2) and passed in at deploy time.
- Done in source: D1 migrations (`apps/gateway/migrations`, applied by `deploy-env.yml`), `ratelimits`,
  the `AuthStore` Durable Object, and `PUBLIC_URL` per environment (`https://gateway-staging.agentlater.io`,
  `https://gateway.agentlater.io`). Agent Auth checks JWT audiences against `PUBLIC_URL`, so it must be the
  hostname agents actually use.
- Staging is routed to `gateway-staging.agentlater.io` (a custom domain in `apps/gateway/wrangler.jsonc`).
  Production is routed to `gateway.agentlater.io`. After each hostname serves, set that environment's
  `GATEWAY_URL`.
- Inbound hooks have a hostname of their own on the same Worker: `hooks-staging.agentlater.io` and
  `hooks.agentlater.io`, the `HOOKS_URL` var per environment. It serves only `/h/…`. The first deploy that
  adds it creates the custom domain; nothing to set by hand.

### Phase 6 — Staging journey

After the smoke check, staging runs [`apps/gateway/e2e/staging.mjs`](../apps/gateway/e2e/staging.mjs): a fresh
agent registers, creates a project, and schedules deliveries to a test receiver
([`apps/receiver`](../apps/receiver), staging only). It checks a signed delivery verifies, a 503 is retried
then succeeds, a 404 fails without a retry, a canceled task is never sent, and idempotent scheduling and
validation work. The same journey runs locally in CI (`npm run test:e2e` in `apps/gateway`).

Once `GATEWAY_URL` is set the journey is required: a failure, or a missing `RECEIVER_URL`/`RECEIVER_TOKEN`,
stops production from deploying. `RECEIVER_TOKEN` comes from the setup script and is passed to the
receiver at deploy time. After the first staging deploy has created the receiver, set the `staging`
environment variable `RECEIVER_URL` to its `*.workers.dev` URL, printed by the deploy
(`https://runlater-receiver-staging.<account>.workers.dev`).

Each run creates a new agent identity and project in staging; they are not cleaned up.

### A2A end-to-end run

The A2A interface is switched on per environment by the gateway's `A2A_ENABLED` var (`apps/gateway/wrangler.jsonc`): on in staging and, since 2026-11-11, in production. After a change to the A2A interface, run [`apps/gateway/e2e/a2a-staging.mjs`](../apps/gateway/e2e/a2a-staging.mjs) against staging and attach its report to the pull request:

```sh
node apps/gateway/e2e/a2a-staging.mjs https://gateway-staging.agentlater.io "$(gh variable get RECEIVER_URL --env staging)" > a2a-report.md
```

It registers a new identity, makes its project, and through the official A2A client checks an immediate and a delayed success, a 404 that fails without a retry, retries exhausted (two 503s with `max_attempts: 2`), cancellation, a duplicate submission, the list, a second host being refused, and that a failed task cannot be redriven. The report is Markdown on stdout, progress is on stderr, and the exit status is 1 if a scenario failed. It takes 30 to 60 seconds. With `RECEIVER_TOKEN` set it also checks what the receiver recorded; without it, deliveries are judged by each task's attempts. It needs the receiver's `down` reply, deployed with the staging receiver.

Each run leaves two hosts and their projects (two of the day's new trials) and six finished tasks, deleted after 30 days. Unlike the journey it revokes its two agents when it ends. It is not part of the deploy workflow and is never run against production while A2A is off there (it would stop at the missing Agent Card).

The same script runs against the local stack in the gateway e2e suite.

### Hosted MCP

The gateway serves `/mcp`, `/authorize`, `/oauth/token`, `/oauth/register` and the OAuth discovery
documents. Its clients, grants and tokens live in the KV namespaces `runlater-oauth-staging` and
`runlater-oauth-production` (created 2026-11-01; ids in `apps/gateway/wrangler.jsonc`), bound as
`OAUTH_KV`. Entries expire on their own: tokens after an hour, grants 30 days after last use,
registered clients after 90 days. The deploy token needs Account · Workers KV Storage · Edit.

### Billing

Agents buy attempt packs through Stripe in two ways: a person pays on `agentlater.io/pay` (Checkout,
`apps/gateway/src/billing.ts`), or the agent pays itself over MPP (`apps/gateway/src/mpp.ts`).
Checkout is on once the secret key, webhook secret and publishable key are set in a GitHub
environment; MPP once the secret key, webhook secret and Stripe profile id are. With neither,
`get_payment_link` answers `billing_unavailable`. Use **test-mode** keys in `staging` and live keys in
`production`. Staging's links also open `agentlater.io/pay`: the page takes the publishable key from
the link, so a test-mode link shows Stripe's test form.

1. Stripe Dashboard → Developers → Webhooks → *Add endpoint*: `https://gateway-staging.agentlater.io/billing/webhook`
   (production: `https://gateway.agentlater.io/billing/webhook`), events `checkout.session.completed`,
   `checkout.session.async_payment_succeeded` and `payment_intent.succeeded` (the last credits an MPP
   charge whose immediate credit failed). Copy its signing secret.
2. In the GitHub environment:

   ```bash
   gh secret set STRIPE_SECRET_KEY --env staging          # sk_test_… (restricted: Checkout Sessions and PaymentIntents: Write)
   gh secret set STRIPE_WEBHOOK_SECRET --env staging      # whsec_… from step 1
   gh variable set STRIPE_PUBLISHABLE_KEY --env staging --body pk_test_…
   gh variable set STRIPE_PROFILE_ID --env staging --body profile_test_…   # MPP; see below
   ```

   MPP needs a Stripe profile (Dashboard → Settings → Profile; the sandbox has its own
   `profile_test_…`) and, for card payments, Shared Payment Tokens, which are in preview: check the
   account is enabled for machine payments. MPP links are signed with a key derived from
   `STRIPE_SECRET_KEY`, so rotating that key invalidates outstanding `mpp_url`s (they last 7 days).

3. Turn on successful-payment emails under Settings → Customer emails in the live Stripe Dashboard, so buyers
   get the receipt a refund asks for.

4. Redeploy. To test on staging: ask for a link with `get_payment_link`, pay with card
   `4242 4242 4242 4242`, then check `get_project` shows `paid: true` and 50,000 more attempts.
   For MPP in test mode, Link's wallet refuses test profiles; use Stripe's validator with a test key
   instead: `MPPX_STRIPE_SECRET_KEY=sk_test_… npx mppx@0.13.5 validate <gateway origin> --endpoint "POST:/billing/mpp/<link>" --body '{}'`.
   It checks the challenge, pays $5.00 in test mode and expects a 200. In live mode,
   `npx @stripe/link-cli mpp pay <mpp_url> -X POST -d '{}' --context "<at least 100 characters>"`.
   The gateway serves `/openapi.json` (the MPP endpoint with `x-payment-info`) and `/llms.txt` for discovery.

A payment that Stripe reports but the webhook could not apply shows as a failed delivery under the
endpoint in the Stripe Dashboard; Stripe retries it for three days, and the gateway logs
`stripe: …` or `mpp: …` in Workers Logs. Each Checkout Session and each MPP PaymentIntent is
applied once. If Stripe gives up (three days
of failures), the customer has paid and has no attempts: credit them by hand or refund in the
Dashboard. Refunds and disputes do not take attempts back.

- **Apple Pay** on `agentlater.io` needs it registered under Settings → Payment method domains.
- **Turning billing off:** deleting the GitHub values is not enough, because deploys keep Worker
  secrets that are left out. Also run `npx wrangler secret delete STRIPE_SECRET_KEY --env <env>`
  in `apps/gateway`.

## Monitoring

[`monitor.yml`](../.github/workflows/monitor.yml) probes production:

- Every 15 minutes: `gateway.agentlater.io/health` (which also checks the API), the site's main, pay and
  legal pages, and that billing is configured: the paid endpoint in `/openapi.json`, and a 400 for an
  unsigned webhook. This doesn't catch a missing `STRIPE_PUBLISHABLE_KEY`, or prove a charge works.
- Daily, and on manual dispatch: the full agent journey against production, delivering to the staging
  receiver. Each run leaves one agent, two trial projects (Agent Auth and hosted MCP) and one OAuth
  client and grant in production.

A failed scheduled check opens a `Monitor: <check> is failing` issue (label `monitor`), which notifies
everyone watching the repository, GitHub mobile included. The next run of that check that passes
closes it; runs in between add nothing, so an outage notifies twice per check, when it starts and
when it ends. Manual runs neither open nor close issues (after a fix, the next scheduled pass closes
it), but cancelling a scheduled run by hand opens one. When health fails, that day's journey is skipped
and its issue is left as it was. If the alert job itself fails, GitHub still emails whoever last
changed the workflow. The daily
run also re-enables the workflow, which in practice resets GitHub's 60-day pause for inactive
repositories (GitHub doesn't document this; if the monitor ever shows as disabled, re-enable it under
Actions). If the monitor itself can't run (GitHub Actions down), nothing
alerts: that is the gap left.

The API, gateway and web Workers have Workers Logs on (`observability` in each `wrangler.jsonc`), so
request logs and exceptions are searchable in the Cloudflare dashboard.

### Numbers

Delivery lateness and usage come from Workers Analytics Engine, which keeps about three months. The
token needs Account Analytics Read, which is not in the deploy token's permissions:

```bash
CLOUDFLARE_ACCOUNT_ID=... CLOUDFLARE_STATS_TOKEN=... node scripts/stats.mjs --days 7
```

Add `--env staging` for staging. `probe` rows are the monitor's journey, delivering to the staging
receiver; `real` rows are everything else.

Reading them:

- A row is written when an attempt is claimed, so a stuck queue writes nothing until it clears, and a
  task abandoned before its first attempt never counts as late. In an outage, falling volume is the
  signal, not p95.
- p95 is weighted by volume, so one project's burst can drive it.
- Under heavy sampling `max_ms` is a lower bound and `packs` an estimate. Stripe has the true payments.

## Rotating `SECRETS_KEY`

Do this if the key may have leaked. It doesn't help if the key is lost: those values are gone. The
design is [ADR 1](adr/0001-rotating-secrets-key.md). GitHub secrets can't be read back, so the key has
two slots, `SECRETS_KEY` and `SECRETS_KEY_2`, and the variable `SECRETS_KEY_SLOT` says which is current;
[`scripts/rotate-secrets-key.mjs`](../scripts/rotate-secrets-key.mjs) only writes them. For one
environment, `staging` first:

1. **Start.** `node scripts/rotate-secrets-key.mjs --env production start` puts a new key in the other slot,
   makes it current and sets `SECRETS_KEY_ROTATING=true`. Deploy. The API now seals with the new key and
   opens with either (the old one as `SECRETS_KEY_PREVIOUS`).
2. **Wait for the sweep.** The gateway's hourly cron reseals 200 projects a run, and the rotation is
   complete once a full pass reseals nothing. From `apps/gateway`:

   ```bash
   CLOUDFLARE_ACCOUNT_ID=<account id> npx wrangler d1 execute DB --env production --remote --command "SELECT * FROM secrets_rotation"
   ```

   `completed_at` set, with `slot` the current slot, means done. `resealed_total` is how many values the
   rotation resealed under the current key (after an `undo`, that's the old one again). `unreadable` counts values no key opens (already broken before the
   rotation); keeping the old key doesn't help them. Set `CLOUDFLARE_ACCOUNT_ID` to the account the Workers
   run in (`npx wrangler whoami` lists your accounts and their ids): wrangler won't choose one when
   your login reaches several, and `finish` always requires it.
3. **Wait an hour more**, for attempts claimed with old ciphertext to finish.
4. **Finish.** `CLOUDFLARE_ACCOUNT_ID=<account id> node scripts/rotate-secrets-key.mjs --env production finish` (needs wrangler logged in)
   sets `SECRETS_KEY_ROTATING=false` and deletes the old slot. It refuses unless that row shows a pass
   completed more than an hour ago, for the current slot, and checked since the slot variables last
   changed: finishing early would delete the only key some values open with. Deploy; the deploy deletes
   `SECRETS_KEY_PREVIOUS` from the Worker, since `--secrets-file` never deletes on its own.

To back out before finishing, run `undo` and deploy: the old key is current again and the new one still
opens, so nothing is lost. The sweep starts a new pass (it reseals back under the old key), and `finish`
waits for it before deleting the new key.

## Lost keys: refund the unused attempts

Someone lost a project's keys or OAuth grant, or the grant expired, and attempts were bought for it. Never
move the project to a new owner: a payment shows who paid, not who owns it, and whoever holds the project
gets its signing secret, inbox and the use of its stored secrets.

A refund is at our discretion and is our estimate. It costs little to get wrong: it goes to the card that
paid, but **it doesn't take the attempts back**, because nothing can remove them, and the project stays on
the paid tier. So someone could claim lost keys and keep spending. That's the risk accepted at $5 a pack;
the rules below limit how often. If claims become common, build a debit first, with safeguards so a payer
can't wipe an owner's balance.

1. **Check the request.** Reply only to the email on the Stripe payment, and say nothing about the project's
   activity before that address confirms. An MPP payment may have no email; decline unless you can tell who
   paid. Refund only what that payment made.
2. **Refuse if:** the project already had a lost-key refund, whoever paid; this payer has claimed before; the
   project was ended for breaking the Terms; or the latest payment is over 12 months old, because the balance
   has expired.
3. **Apply the 14-day refund first.** Within 14 days and under 1,000 of the pack's attempts used, the Terms
   promise the whole pack back.
4. **Count what was bought.** Use Stripe, not the report. Metadata names the project: `project_id` on a
   Checkout session, `runlater_project_id` on an MPP PaymentIntent. Leave out packs already refunded, and any
   pack that expired before the next purchase, because it was forfeited then. Compare with the report's
   Payments row to spot another payer.
5. **Count what was used**, adding the `real` and `probe` rows, with `--project` limiting the report to one
   project. An empty table means no rows, which isn't proof of no use:

   ```bash
   CLOUDFLARE_ACCOUNT_ID=... CLOUDFLARE_STATS_TOKEN=... node scripts/stats.mjs --days 92 --project prj_...
   ```

   This keeps about three months and starts on 2026-11-05, and a lost write can only make it low. For a
   payment older than that the count can't be trusted, so offer a refund only if you have other evidence
   of what's left. The Terms make no promise beyond 14 days.
6. **Work out the refund.** Bought minus used, leaving out the 100 free trial attempts, at 10¢ per 1,000,
   rounded down to the cent. Take it from the newest payment first, never more than a payment's amount.
7. **Refund it in the Stripe Dashboard**, as a partial refund, and keep the emails. A cron left running keeps
   spending, and there's no way to stop it without the keys, so a project with crons may use attempts you
   refunded.

## Rollback

```bash
npx wrangler rollback --env production
```

Run it in the affected app's directory. Roll back the gateway before the API if the internal contract
changed. Durable Object migrations and D1 migrations are forward-only, so ship schema changes that the
previous Worker version can still read.

## The rename from RunLater

The product was RunLater and is now AgentLater. Two domains stay live.

- **Old hosts keep serving.** The gateway Worker answers on both domains. `ALT_PUBLIC_URL` and `ALT_HOOKS_URL` name the old hosts, and `apps/gateway/src/hosts.ts` gives each request the URLs of its own host, because OAuth and Agent Auth bind tokens to them. Rolling back is swapping these values with `PUBLIC_URL` and `HOOKS_URL`.
- **No redirects on the gateway or hooks hosts.** Webhook senders and MCP clients POST, and they don't reliably follow redirects. Only the site redirects.
- **`hooks.runlater.io` stays indefinitely.** Hook URLs are shown once and stored only as a hash, so they can't be reissued.
- **`gateway.runlater.io` stays** at least 12 months after the last pack sold through it, matching pack validity. Check traffic before removing it. Keep `runlater.io` registered.

These kept the old name on purpose:

| Identifier | Where | What changing it breaks |
| --- | --- | --- |
| `runlater/secrets/v1` salt | `apps/api/src/sealing.rs` | Stored secrets become unreadable |
| `runlater-mpp-link`, `runlater-mpp-challenge` | `apps/gateway/src/mpp.ts` | Outstanding MPP links stop verifying |
| `runlater_project_id`, `runlater_attempts` Stripe metadata | `apps/gateway/src/mpp.ts` | MPP payments in flight can't be applied |
| `RunLater-*` delivery headers and reserved prefix | `crates/egress` | Receivers verifying signatures fail |
| Worker names, including `runlater-api-*` | `wrangler.jsonc` | Durable Objects and their ledgers are tied to them |
| D1, KV, queue and dataset names; `runlater_project` | `wrangler.jsonc`, migrations | Data is orphaned |
| `runlater-api` audience, `RunLater-Assertion`, `RunLater-Project`, `RunLater-Via` | Gateway and API | Internal only; no benefit |
| `@runlater/*` packages, `runlater-*` crates | Workspace | Internal only; no benefit |

The Claude Code plugin `plugins/runlater` and registry entry `io.github.thachp/runlater` are deprecated rather than removed. Installed copies keep the server address they were given.
